## 5. Bugs, errors and unresolved issues

Pre-existing in mirage (reproduced on the untouched baseline, not caused by the redesign):
- **B4** Wikipedia article pages reload repeatedly (a Wikipedia script warning, `movePinnableElement`, is only noise). Cause unknown; possibly a Scramjet alpha.1 issue. **Update 2026-11-22:** with Scramjet 2.1.0 an article loaded once; the loop was not specifically checked.
- **B8** `httpbin.org/cookies/set?a=1` fails with Scramjet's "attempted to fetch from same origin" error; the page ends at `localhost/httpbin.org/cookies/set?a=1`. **Cause found and fixed 2026-11-22 (commit `8e732a5`):** the address was typed without `https://`, and mirage's `norm()` returned any input starting with `http` unchanged, so `httpbin.org/...` (also `http2.pro`, `httpstat.us`) became a relative address on localhost; `isUrl()` had the same `startsWith("http")` test. Both now test `^https?://` (not protected logic). Re-tested in headless Edge: `httpbin.org/cookies/set?a=1` ends at `https://httpbin.org/cookies` and shows `{"cookies": {"a": "1"}}`. The earlier note that `norm()` was not the cause was wrong. A related display bug was fixed in the same commit: in the dark theme a proxied plain-text or JSON page (robots.txt, the cookie JSON) has white text and the white canvas behind proxied pages made it look blank; the canvas is now only for HTML documents (`watchFrame` in `index.html`). Not yet confirmed in the user's Chrome.
- **B10 (fixed 2026-11-23, approved; not yet confirmed in the user's Chrome)** YouTube pages failed with an Epoxy/hyper HTTP/2 error (`Reset(StreamId(n), PROTOCOL_ERROR, Library)`). **Cause, confirmed in source and by measurement:** hyper 1.6.0 (inside epoxy-tls) limits an HTTP/2 response header list to 16,384 bytes (`DEFAULT_MAX_HEADER_LIST_SIZE`, counted as name + value + 32 per field), and h2 0.4.7 answers an over-size response with `library_reset(id, PROTOCOL_ERROR)`, exactly the error seen. Measured over HTTP/2: YouTube's HTML pages 20,493 to 20,529 bytes, Discord 8,820, Google 3,309, robots.txt 1,041. No option could change it from outside (`EpoxyClientOptions` has no HTTP/2 setting, ALPN is hard-coded `h2` then `http/1.1`, the minimal build has no WebSockets). **Fix:** epoxy-tls rebuilt with `http2_max_header_list_size(256 * 1024)` (Chrome's `kSpdyMaxHeaderListSize`), see the Done entry in section 7. The baseline note "B10 loads then video fails" (M1) does not fit: epoxy-tls 2.1.19 had the same hyper 1.6.0 and limit, so YouTube's headers probably grew since. Original entry: Reproduced 2026-11-22 with a bare GET through the transport on any wisp server: `www.youtube.com/`, `/feed/trending`, `youtu.be/...` and even HEAD fail every time, while `/robots.txt`, `i.ytimg.com`, Google and Discord work (`httpstat.us/200` hit the same error too). Likely cause, not proven: YouTube's HTML response headers are large (about 12.8 KB measured against about 1 KB for robots.txt) and epoxy-tls (hyper/h2) exposes no HTTP/2 header-list-size setting (only `header_limit`, which is HTTP/1); the Servo project reported the same signature on YouTube in Nov 2026. A real fix needs a rebuilt `epoxy/index.js` (protected, needs approval); no adapter can fix it. A retry does not help. Pre-existing on the baseline. B11 variant (discord.com/app after a worker stop gave this error once, a refresh worked) could not be reproduced.
- **B17 (found and fixed 2026-11-23, reported by the user while checking B10):** every proxied page, YouTube or not, showed `Cannot GET /~/sj/<controller>/<frame>/<address>` on Live Server. *Cause (reproduced, headless, npm `live-server`, a profile with the pre-M9 `loader-sw.js` registered):* opening the localhost copy installed the newer `loader-sw.js` (changed in M9) while the shell started; the controller stays bound to the worker object it was given (`serviceWorkerController`), now redundant, so its port and every retry (`setupMessagePort`) went to the dead worker and the new one had no routes. The same can happen to `index.svg` users when a release changes `loader-sw.js`. Not caused by the new `epoxy/index.js` (fresh profiles worked). *Fix (in `index.html`, outside the protected logic):* `followWorker` re-points `serviceWorkerController` at `navigator.serviceWorker.controller` and calls `setupMessagePort()`, on `controllerchange` once ready and inside `retryUnserved`. Tested: the stale-worker reproduction now loads example.com and YouTube (one `[paroxysm] the service worker was replaced` warning); a fresh profile, a hard reload and a normal reload still work. Not tested in the user's Chrome yet; a plain reload (F5) also clears it.
